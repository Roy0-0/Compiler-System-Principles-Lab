# 程序 C 纯内核实验分析

## 为什么增加程序 C

程序 B 的计时覆盖进程启动、内存分配、初始化、变换、校验和与释放，适合端到端比较，但不足以单独评价 `transform`。程序 C 在一次进程内完成初始化，然后只围绕 `transform` 计时；每个变体使用 500 万元素、20 次内核重复、7 轮独立运行，并报告 `ns/element` 中位数。

每轮计时结束后，程序使用独立参考计算核对校验和。九个变体均得到 `546687110` 且 `verified=1`。

## 最新结果

| 变体 | 线程 | 中位 ns/element | 相对基准 |
|---|---:|---:|---:|
| Clang 关闭向量化 | 1 | 0.474286 | 1.00× |
| Clang 自动向量化 | 1 | 0.428837 | 1.11× |
| Clang `restrict` | 1 | 0.402262 | 1.18× |
| GCC `-O3` | 1 | 0.396880 | 1.20× |
| GCC LTO | 1 | 0.406891 | 1.17× |
| OpenMP | 1 | 0.436563 | 1.09× |
| OpenMP | 2 | 0.237620 | 2.00× |
| OpenMP | 4 | 0.165114 | 2.87× |
| OpenMP | 8 | 0.111521 | 4.25× |

相对基准以 Clang 关闭向量化版本计算。线程扩展还可相对 OpenMP 单线程表示为约 1.84×、2.64×、3.91×，没有达到理想线性加速。这与线程启动/同步开销和内存带宽共享相符，但当前没有硬件计数器，因此只作为合理解释，不写成已直接测量的因果结论。

## 编译器证据

- Clang 明确报告 `transform` 循环以向量宽度 4、interleave count 2 完成向量化；
- GCC 报告同一循环使用 16 字节向量，并因可能别名生成运行时版本；
- `restrict` 没有在本轮形成稳定性能优势，说明额外别名信息不必然改变最终瓶颈；
- GCC LTO 在最终复测中没有优于 GCC `-O3`；该程序只有一个翻译单元，跨翻译单元优化空间很小；
- OpenMP 8 线程仍继续加速，但远低于 8 倍，表现出非线性扩展。

## 仍保留的边界

当前 WSL 环境没有可调用的 `perf`，`perf_status.txt` 为 `UNAVAILABLE`。cycles、instructions、IPC、cache misses 和 branch misses 尚无实测值。后续安装并允许访问性能计数器后，可直接复用程序 C 采集这些指标。
